# Autobee session traces

Generate from the repository root with `node fixtures/gen/record/run.mjs` after installing `fixtures/gen` dependencies. These are recordings of autobee 2.12.1 sessions, not synthetic Rust expectations. Corestores use distinct fixed test-only primary keys; these are public fixture identities, never production secrets. `Date.now` and Autobee's `now` read a logical clock advanced once per append, eliminating wall-clock dependence. Replication uses in-process Corestore streams and explicit writer wakeups. Temporary storage paths never enter the JSON.

Each JSON file is an object with `schema: 1` and `scenario`. All byte strings, including keys, node values, hashes, raw blocks and KV entries, are lowercase hexadecimal; `null` retains its JS meaning. Each peer is identified by `a`, `b`, or `c`.

- `peers`: peer ID to `{writer, oplog, stats}`. `writer` is the local writer key; `oplog` is `{key, blocks}` with raw blocks in ascending sequence order. `stats` records `undos` and `fastForwards`.
- `steps`: scripted `append` (decoded operation and optimistic flag), `connect`, `sync`, and `disconnect` inputs in order. Disconnect closes all current streams.
- `topology`: actual calls to wrapped `topo.sort` and `topo.linearize`. Each has `peer` (null for `linearize`), `method`, `batches` (input batches of decoded nodes), `list` (output batches), `undo`, and `view`. For `sort`, `batches` contains the incoming batch; any previously applied batches retrieved internally appear in `list`, not as inputs. Calls not made by a scenario are absent.
- `hashes`: each actual system `addNode` hash transition, `{peer, prev, node, result}`. This surrounds the private `advanceHash` call; `prev` can be null. The input node includes the key, length and weight used by the hash.
- `flushes`: each system flush, `{peer, batch, preHead, updates, puts, info, system, view, systemHead, viewHead}`. `preHead` is the system bee head immediately before flush, and `updates` is the ordered collection of pending writer-update objects at that point (after `addNode` and handler mutations). `puts` is the ordered sequence of raw system bee `put` and `delete` operations (`key`, and `value` for puts). `info` is the decoded value actually read back from system key `00`. `system` and `view` are `{key, blocks}` snapshots of the respective local physical cores after the flush, including blocks made unreachable by undo; heads identify the logical tree roots and may reference other cores. A head length is not necessarily the local physical core length.
- `apply`: each actual handler invocation, `{peer, nodes, host}`. `host` records invoked `addWriter`/`removeWriter` calls and their arguments. The handler accepts owner grants/revocations and performs simple view puts; it is not the full PearTube authorization protocol.
- `fastForward` appears only in the landing scenario. `candidates` records each actual `fromHeads` invocation, its oplog heads, trust `decisions` and selected system head (or null). `trust` records calls to the PearTube-style trust hook; the candidate decisions also include cached and genesis trust results that bypass that hook. `landing` records the system and view heads, decoded system info and complete logical system/view KV state. `downloaded` records each relevant core's advertised length, target length, and the exact locally present block indexes observed immediately after landing, before the KV scans. Scans may fetch more blocks. `seenByOwner` is the owner's resulting view entry after the joiner's append.

Nodes preserve the relevant npm node fields: key, length, weight, version, timestamp, links, batch, views, value, hash, witness, optimistic and approvals where present. Binary values nested in these objects are hex. Fields omitted by npm remain omitted. The event arrays are grouped by peer, preserving each peer's execution order; no global ordering between independently running peers is implied. `steps` alone has global scripted order.

## Scenarios

- `single-writer`: three local puts, including an overwrite.
- `concurrent-writers`: two granted writers append while disconnected and replicate in two rounds.
- `add-remove`: the owner grants a second writer, adds a third mid-stream, then revokes the second.
- `optimistic`: an unknown writer appends optimistically before the owner's grant, then writes after confirmation.
- `reorder`: the second writer's older concurrent append arrives after two later owner writes; an assertion requires an actual undo.
- `late-joiner`: a reader joins after 48 owner operations and must observe the final value. Fast-forward is disabled to make this a deterministic full-history baseline for fast-forward comparisons; it does not claim to exercise an actual fast-forward landing.
- `fast-forward-landing`: an offline joiner is granted before 24 additional owner writes, then connects with fast-forward enabled and owner trust configured. The recorder gates the joiner's apply drain until the actual candidate search has scheduled its landing, avoiding a race with full replay; it then releases the drain, records the landed state and checks that an append by the joiner reaches the owner. This gate controls scheduling, not trust or landing selection.
